enList v3 Pre-sales roadmap To the enList team 15 Sep 2026

Ten sprints to sellable.

The sales brief found enList a strong engine that a buyer can't get through: they can't try it on what they already run, it fails a security review, a pilot finds gaps, and there is nothing to buy. These ten sprints clear those four stages in order. Each ends with automated tests that prove it is done, and each makes the next one possible. The first two make the codebase safe to change; the last one makes it possible to invoice.

Assumptions
  • Two-week sprints, three engineers who know the codebase.
  • Done means the acceptance tests are automated and green in CI, plus the live checks named.
  • Every sprint ends in a demo someone outside the team could follow.
  • Sizing is judgement, not measurement. Sprints 3, 4 and 9 are the fullest: when one runs long, cut its last scope item, never its tests.

Twenty weeks. The order is the buyer's path from the sales brief: they try it, pilot it, send it through a security review, then purchase. The two foundation sprints come first because every sprint after them changes code that runs on every managed machine.

Start now, outside the sprints

Five things with long lead times that no sprint can hurry.

  • Buy the code-signing certificateSprint 10 signs every file. Validation of the organisation can take weeks.
  • Recruit three to five design partnersThey start at the end of sprint 5, and their pilots shape sprints 6 to 9.
  • Validate the pricing hypothesisPer managed machine, per year — tested with those partners before sprint 10 builds it in.
  • Draft the EULA and trial termsLegal work, needed as text by the start of sprint 10.
  • Settle the design's open questionsProgram-Workloads-Design §18, before sprint 3 writes the code that depends on them.
The ten sprints

What each one builds, what it fixes, how we know it's done, and why it comes next.

1Foundation

The safety net

Every change after this one lands on an automatic gate, and a shutdown defect in today's agent is fixed.

Value

Sprints 2 to 10 all touch code that runs on every customer machine, and the agent can't update itself. This turns a regression from something a customer finds into something CI finds in minutes. The shutdown fix removes a defect the very first customer upgrade would hit.

Sprint 2 changes the runner protocol and the installer's permissions. Both are exactly the kind of change that needs this gate first.

Scope
  • Minimum CI on a Windows runner with Docker. It rebuilds enlist/runner:dev from source, runs dotnet test enList_v3.slnx and verify.ps1, and fails when a container test skips.
  • Characterization tests for paths nobody tests today:
    • portal Start/Stop through the hub, to the runner and back;
    • job Enable/Disable with an in-flight cancel;
    • agent shutdown with several applications;
    • the protocol-mismatch messages;
    • the heartbeat.
  • Fix agent shutdown: stop applications in parallel, set HostOptions.ShutdownTimeout explicitly, and request more time from the Service Control Manager while stopping.
  • Bring Test-Plan.md up to date: it still says 273 tests.
Issues it solves
  • No CI. Every test, check and live run is manual, and container tests silently skip without Docker.
  • Untested paths. The Test Plan admits imperative commands and the heartbeat have no automated tests.
  • Shutdown overruns. The agent stops applications one at a time, 10 s each, with no host timeout set, so sc stop or an MSI upgrade can kill runners mid-stop.
Done when
  • CI runs on every push and blocks a red merge; a run without Docker fails instead of skipping.
  • The characterization tests pass on main both before and after the shutdown fix.
  • Four applications, each needing 20 s to stop gracefully, all stop in about 20 s with none killed, and sc stop enlist-agent reports no timeout.

Not in this sprint: live-e2e.ps1 in CI — it needs a disposable, elevated machine and stays a release gate.

2Foundation

Harden the foundation

Close the agent's known permission gap, and let the runner protocol grow without breaking container images already in the field.

Value

A security reviewer who runs icacls on the agent's folder finds nothing to write up. Program hosting in sprint 3 is built on folders and a protocol that are already safe, not fixed after the fact.

Sprint 3 runs arbitrary customer programs, as SYSTEM, out of these folders. It must not start until they are locked.

Scope
  • Installer: lock Packages\, Runners\ and AppData\ under the agent data folder to SYSTEM, Administrators and the agent's account, each in its own component so reinstalls and upgrades apply it; verify.ps1 checks it.
  • Runner protocol 3, with optional fields: HostingKind, StopGraceMs, and per-service pid, exit code, restart count and detail. The agent accepts both 2 and 3, and the legacy runner is not touched.
  • The agent honours an application's StopGraceMs; CrashBackoff moves into the runner assembly.
  • live-e2e.ps1 on a fresh install, an upgrade over the previous build, and an agent under a named account.
Issues it solves
  • DLL planting. Ordinary users can create files where the agent stages executables that run as SYSTEM (confirmed with icacls).
  • A 10-second ceiling on every application's shutdown.
  • Exact protocol matching would fail every container application whose runner image shipped separately.
  • Named-account agents have never been run for real.
Done when
  • verify.ps1 shows the three folders protected, by components that are neither Permanent nor NeverOverwrite.
  • live-e2e.ps1 passes on a fresh install, an upgrade, and a named-account agent.
  • A container application on today's enlist/runner:3.0.0 image (protocol 2) still runs under the new agent.
  • An application reporting a 30 s grace period is given 30 s, not 10.

Design: Program-Workloads-Design §8, §9 and §16 phase P0; its risk register is §16.1.

3Try it

Programs run: services

The runner keeps an unmodified program running as a service, on real Windows behaviour, proven rather than assumed.

Value

This is the technical heart of the sales plan. The riskiest questions come first:

  • Does Ctrl+C reach a program with no console window?
  • Does a batch file end cleanly?
  • Are grandchild processes contained?

The demo: a .NET 4.8 console service, a PowerShell 7 loop and a windowed program, kept alive by an agent. Kill them in Task Manager and they come back.

Sprint 4 adds jobs, and puts program packages behind the control plane and the deploy tool.

Scope
  • contracts/WorkloadDescriptor.cs: the enlist.workload.json model and one validator, shared by the runner, control plane and deploy tool.
  • The runner's program host:
    • processes created inside their job object;
    • stdout and stderr turned into logs, with the UTF-8/OEM heuristic, CR handling, truncation and a rate guard;
    • stop escalation: Ctrl+C through a signal helper, then stdin, then WM_CLOSE, then a stop command, then terminate the tree;
    • restart policies with backoff and give-up;
    • a readiness pattern;
    • windowed-program detection;
    • a private app copy, a data directory, and a warning naming files written beside the program.
  • The agent routes the program flavor to the modern runner, behind --program-workloads, off by default until sprint 4.
  • enlist-runner --check and --dev work on descriptors.
  • tests/Enlist.TestPrograms: console and GUI test programs, plus test scripts.
Issues it solves
  • The number one deal blocker: only code written against enList's attributes can run.
  • Windows behaviours the design only assumes, proven or disproven while there is time to change course.
Done when
  • The stop-and-containment matrix passes for services (S1–S16).
  • Use case UC-1 passes end to end through a real agent, driven by a local --assignments file, with no control plane changes needed yet.
  • The full existing suite is unchanged and green.

Not in this sprint: jobs, control plane detection, the portal. Design: §6, §7, §9.1.

4Try it

Programs run: jobs, the control plane and the CLI

Package a folder of scripts, upload it, place it by rule, and watch it run and fire on schedule, end to end.

Value

A design partner's engineers can run a real evaluation from the command line. The fleet-wide off switch exists before anyone outside the team runs a program under enList, so there is a way back from any surprise.

Sprint 5 gives it a face in the portal and an onboarding path someone new can follow on their own.

Scope
  • Jobs: cron, timeoutMinutes, successExitCodes, cancellation, {runId}, per-run settings as ENLIST_SETTING_*.
  • Control plane:
    • the descriptor is detected before .deps.json;
    • the manifest gains kind, declared cron, command and warnings, and cron from attribute packages too;
    • an upload returns 400 listing every error;
    • rules refuse containers for programs and check cron-override job names;
    • capabilities list runtime flavors.
  • The fleet-wide switch: ProgramWorkloads:Enabled.
  • enlist-deploy: validates before uploading, adds check, and hints "this looks like a program".
  • live-e2e.ps1 deploys a PowerShell job and a console service to an installed agent. The agent switch then defaults to on.
Issues it solves
  • The try-it blocker, removed at the API and CLI.
  • Scripts-only zips labelled net472.
  • Cron overrides never checked against real job names.
  • Capabilities never used by the control plane.
Done when
  • Use cases UC-2 and UC-3 pass as automated agent tests.
  • The control plane tests pass: detection order, all errors at once, program-in-container refused, switch behaviour.
  • The live run's program phase passes on an installed agent.
  • Switching ProgramWorkloads:Enabled off stops program workloads on installed agents with no agent action, and on again restarts them.

Design: §6.6, §7.7, §10, §12. Watch: the fullest sprint so far. If it runs long, cut the check subcommand, not the switch.

5Try it

Evaluate in an afternoon

Someone who has never seen enList runs one of their own programs under it, in under an hour, with only the guide to help.

Value

The try-it stage is open. The mock-up on the "Run What You Have" page becomes a screenshot.

Sales milestoneDesign-partner pilots start.

Pilots on real estates will surface the operational gaps sprint 6 exists to close.

Scope
  • Portal:
    • Program and SDK chips;
    • the Packages page shows manifest and kind;
    • the rule wizard fixes process isolation and picks jobs from the manifest;
    • the instance table shows pid, restarts, last exit code and detail;
    • jobs show last run and outcome;
    • a Disabled chip;
    • a warning for matching agents that can't host programs;
    • the upload dialog shows warnings and errors.
  • enlist-deploy init writes a starter descriptor.
  • A Program Workload Guide in docs/02-building-applications, including the three watch-outs.
  • Samples: a console service, a PowerShell job, a batch file with a success range, and a descriptor-only package adopting installed software.
Issues it solves
  • The Packages page shows no manifest and no flavor today.
  • A job's last run is reported but shown nowhere.
  • Onboarding means reading a design document.
Done when
  • Portal tests cover the new chips, columns, wizard behaviour and warnings.
  • Every sample passes enlist-runner --check in CI.
  • A moderated test: a person new to enList completes UC-5 in under 60 minutes using only the guide, with the time and every place they got stuck recorded.

Design: §11, §12, §16 phase P2.

6Pilot

Control that sticks, history that stays

What an operator does in the portal holds across restarts, and what a job did last week can be looked up.

Value

Operators stop reaching for remote desktop to double-check. Task Scheduler has a History tab, and without one enList looks weaker than what it replaces. The run records this sprint creates are what sprint 7 alerts on.

Sprint 7 turns the failures now recorded into notifications.

Scope
  • Operator overrides that last: a portal Stop of a service or Disable of a job is stored centrally with who and when. It survives application restarts, agent restarts and redeploys, until someone clears it.
  • Job run history:
    • a JobRuns table: application, agent, job, run id, start, end, outcome, exit code, duration, error line, trigger;
    • a retention setting;
    • a per-job history view with an outcome filter.
  • Run now, and run now with parameters, from the portal and the API. Jobs with no schedule become usable.
  • The first database migration since InitialCreate, with its upgrade path.
Issues it solves
  • A stopped service comes back after an application restart (SAD §9.1).
  • Only a job's last run is kept.
  • No way to run a job on demand.
Done when
  • Stop a service, restart the agent and redeploy: it stays stopped, and the portal says who stopped it and when.
  • A hundred runs are recorded with correct outcomes and exit codes, and the retention sweep removes the old ones.
  • Run now with k=v reaches the program as ENLIST_SETTING_K, and an overlapping tick is still skipped.
  • The migration applies to an upgraded database in the live run.
7Pilot

Alerts: know before the customer calls

Failures reach a person, not just a screen someone has to be looking at.

Value

This turns enList from a dashboard into an operations tool. Alerts are one of the strongest reasons to buy over Task Scheduler, and they are on every security checklist.

Sales milestonePilots run unattended.

With failures recorded and routed, sprint 8 answers the security review's "who did this?" and "who can do this?".

Scope
  • Alert conditions:
    • a service Faulted or given up;
    • a job Failed, timed out, or missed its schedule;
    • an agent offline;
    • an application Failed (conflict, disabled);
    • program workloads switched off.
  • Channels: email (SMTP), Microsoft Teams (a webhook URL), and a generic webhook with a JSON body and HMAC signature.
  • Scoped by application and tag; deduplicated and throttled; a resolved notice on recovery.
  • Portal: alert rules and channels, a test-send button, alert history.
Issues it solves
  • No alerts of any kind (sales brief, pilot and security stages).
  • The story every prospect tells: it stopped after Windows Update, and nobody noticed for a day.
Done when
  • An injected fault produces an email, a Teams message and a webhook call within 60 seconds.
  • A flapping service raises one notification per incident, not one per restart.
  • Recovery sends a resolved notice, and a missed schedule raises an alert.
  • Webhook signatures verify against a published algorithm.

Not in this sprint: PagerDuty or Opsgenie integrations — a generic webhook covers them until customers ask.

8Security review

SSO, roles and audit

A security reviewer's identity and accountability questions get a straight "yes".

Value

Required for cloud-first organisations with no on-premises Active Directory. It answers "who changed this rule, and when?" — the first question after an incident, and the one regulated customers must be able to answer.

Sprint 9 builds secrets on this base: who may read or set a secret has to be role-controlled and audited from the first line.

Scope
  • Entra ID / OIDC sign-in for the portal, alongside Windows sign-in, with group claims mapped to roles.
  • Three roles — Viewer, Operator, Administrator; keys, join tokens, switches and alert channels move to Administrator.
  • Optional per-application scope by tag: the finance team operates finance applications only.
  • An audit table recording every change: who (person or key), what, a before-and-after summary, when, from where. A portal page with filters, CSV export and retention.
  • API keys show their role, scope and expiry.
Issues it solves
  • Sign-in by on-premises Windows groups only.
  • Only two roles.
  • Audit is log lines, not records, a gap Authentication-Design §16 deliberately deferred.
Done when
  • OIDC sign-in works against a test identity provider running in CI.
  • A test walks the endpoint policy table and asserts every endpoint's role.
  • A test asserts every changing endpoint writes an audit record.
  • A scoped operator cannot command an application outside their scope.
9Security review

Secrets and run-as

Programs get their credentials without anyone putting them in a package, and don't have to run as LocalSystem.

Value

The security review's two hardest questions get answers. It is also a pitch of its own for legacy estates: take the passwords out of your scripts.

Sales milestoneSecurity questionnaire passable.

With the security review clear, sprint 10 makes enList something a customer can actually buy.

Scope
  • Secret store in the control plane:
    • encrypted at rest with a certificate, not machine-only encryption, so it survives a move to more than one control-plane node;
    • versioned;
    • never returned in plain text;
    • managed by Administrators, with every read and write audited.
  • Delivery: a descriptor or rule refers to a secret by name, and it reaches the program as an environment variable at start, or SDK applications as a setting. Known secret values are redacted from logs.
  • Run-as for programs: group-managed service accounts first (no password to store), then a stored credential.
Issues it solves
  • No secrets store: settings are plain JSON.
  • Every program runs as the agent's account, the largest remaining risk in the program workloads design (§13).
  • Hard-coded passwords in legacy scripts.
Done when
  • A secret's value appears in none of these:
    • the package;
    • the logs (a redaction test);
    • the process command line;
    • the status report;
    • any API response.
  • A program runs as the configured managed service account, proven by the process owner.
  • A rotated secret reaches the program at its next start.
  • Every secret read and write has an audit record.

Watch: a full sprint. Azure Key Vault references and stored-password run-as are the first things to move to sprint 11 if it runs long.

10Purchase

Licensing, trial and a signed installer

A customer downloads a signed installer, trials it, and buys a license that enList enforces fairly.

Value

The purchase stage exists. An unsigned installer draws a SmartScreen warning, which ends most trials before they begin; a signed one looks like software a business can buy.

Sales milestoneFirst paid license.

The sales motion begins. Everything after this is driven by what paying customers ask for first.

Scope
  • License keys:
    • signed and checkable offline;
    • edition, managed-machine count, expiry;
    • enforced at enrollment with a grace period and portal banners;
    • never stops an application that is already running.
  • A 30-day trial license at install, and a portal page showing usage against entitlement.
  • Installer: the license-agreement page in the wizard (Installer-UI-Design §6.2); Authenticode signing of the setup, the MSIs and every executable in build.ps1; verify.ps1 checks the signatures.
  • Release kit: versioned downloads (setup, runner image, READMEs), a release-notes template, and CI/CD examples for GitHub Actions and Azure DevOps using enlist-deploy.
Issues it solves
  • Purchase: nothing built. No license key, EULA, pricing, trial or CI/CD examples.
  • Unsigned installers (Installer-UI-Design §12 item 7).
Done when
  • Tampered, expired and over-count licenses are each refused or put into grace, as specified, in tests.
  • A simulated trial expiry leaves running applications running.
  • verify.ps1 and Get-AuthenticodeSignature confirm every shipped file is signed.
  • The license page renders and must be accepted in the wizard.
  • The example pipelines deploy a sample to a test control plane in CI.

Depends on the certificate, EULA text and pricing decision started at the top of this page.

Deliberately after sprint 10

Next in line — and why each one waits.

All real, all worth building. None of them stops a first sale, and each is better shaped by what paying customers ask for.

  1. Gradual rolloutsCanary by tag with a health gate and automatic rollback. Two rules on different tags cover it until then.
  2. Agent self-updateFleet upgrades without a per-machine MSI. Until then, customers already push MSIs with SCCM, Intune or Group Policy.
  3. A highly available control planeA SignalR backplane and a shared package store. Running agents keep working while the control plane is down.
  4. Health probes and resource limitsProgram workloads phase P3: HTTP/TCP liveness, and memory and CPU caps on the job object.
  5. Wider reachAdopting services the Windows Service Control Manager owns, programs in containers, and Linux agents.
