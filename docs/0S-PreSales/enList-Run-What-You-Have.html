  1. A
    A Program, not a rewrite

    LegacyInvoicing is a folder of VB6, VBScript and PowerShell plus one small JSON file. It is versioned and deployed like any enList application — this is its seventh upload.

  2. B
    Services and jobs, whatever they are written in

    A 2004 VB6 executable is listed per server as a service, and a VBScript and a PowerShell script as jobs — the same rows, badges and buttons as SDK code.

  3. C
    The real process id

    6120 is INVPRINT.EXE itself, not a wrapper, so Get-Process -Id 6120 on FIN-APP-01 finds exactly what the portal shows.

  4. D
    It came back on its own

    After six days INVPRINT crashed with an access violation. enList wrote down the exit code in words and restarted it two seconds later. The restart count is on the row.

  5. E
    It knows what it's running

    INVPRINT has a window. enList read that from the executable and says so, because a windowed program on a server can't show anyone a dialog — the kind of thing worth knowing before 2 a.m.

  6. F
    Failed means failed

    Not Last Run Result: 0x1. The export failed at 02:00 with exit code 1, and the reason is one line away in the log.

  7. G
    Warnings arrive as warnings

    PowerShell's WARNING: lines are logged at Warning, without the script changing — so twelve skipped invoices don't hide among the routine lines.

  8. H
    Knows when to stop trying

    Label Printer Bridge can't load a DLL on WH-APP-01. After five quick failures enList stops restarting it, says why, and offers Start once the DLL is back.

  9. I
    Success, by the program's own rules

    robocopy exits 3 when it copied files. The package says codes 0–7 are success, so this run reads Succeeded, not Failed.

  10. J
    Placed by rule, not by hand

    Order Listener runs wherever a server carries role=orders. Tag a sixth warehouse server, and it starts there too.

  11. K
    Old and new, side by side

    An application built on the enList SDK sits in the same list, so modernising one program changes nothing about how the others are run.

  12. L
    Uploaded, not yet placed

    PayrollBridge is in enList but runs nowhere until someone adds a rule. The warning says so rather than leaving it to be discovered.

No SDK. No rewrite. One file beside the program.

Why run them through enList

Your programs don't change. What you know about them does.

Each of these is something an operator does by hand today, set against what enList does instead. The markers point back to where the mock-up shows it.

Deploy once, not fourteen times J

Today

Remote desktop into each server, copy the new build over the old one, and hope none of them was skipped.

With enList

One upload and one rule by tag. Every matching server picks it up, and a server added to the pool next month does too.

See that it's running C

Today

Sign in to the server, open Task Manager, look for the process by name — on every server, one at a time.

With enList

Every program on every server, in one list, with its state and its real process id, refreshed every few seconds.

Know when it didn't work F

Today

Task Scheduler says 0x1. Nobody looks until the finance team asks where the export went.

With enList

Failed, exit code 1, and the line that caused it. Success is judged by the program's own exit codes, so robocopy's "3" isn't mistaken for a failure.

It comes back by itself D

Today

NSSM restarts it on the servers where someone installed NSSM. Everywhere else, it stays down until someone notices.

With enList

Restarted with backoff on every server. After repeated failures it stops trying and says why, instead of spinning forever.

Logs in one place G

Today

A text file on the C: drive of each server — if the program writes one at all.

With enList

Every line a program prints, from every server, in the portal, with warnings and errors marked as such, and a live tail.

Change a schedule without a server

Today

Edit the scheduled task on each server, and hope the trigger was set the same way on all of them.

With enList

Change the cron on the rule. enList checks the job exists and the schedule is valid, and every matching server follows.

Roll back in a minute A

Today

Find the previous build — if anyone kept it — and copy it back to every server again.

With enList

Point the rule at the previous version. Every upload is numbered and fingerprinted, and kept for 30 days after nothing uses it, so last week's build is one click away.

Leave legacy code alone K

Today

Modern operations seem to require modern code, so the VB6 tools wait for a rewrite that never gets funded.

With enList

VB6, VBScript, PowerShell 5.1 and .NET Framework run exactly as they are, each in its own process — and can be rewritten one at a time, later, on the SDK, in the same list.

Safer by design E

Today

Scripts run under whatever account set them up, on servers people remote into for routine jobs.

With enList

Agents only dial out. Every process tree is contained, so nothing is left orphaned, and only Operators can deploy or change what runs. No remote desktop session is needed for any of it.

Getting there

From a folder of old programs to the fleet, in an afternoon.

The same steps whether it is one script or fifty. Rough times, for someone who has installed enList and never packaged a program before.

  1. Describe it

    about 10 minutes enlist-deploy init --source .\LegacyInvoicing --service INVPRINT.EXE

    Writes the descriptor. Add the jobs and their schedules.

  2. Watch it locally

    about 15 minutes enlist-runner --dev --app .\LegacyInvoicing

    Start it, stop it, run a job — under enList's supervision, on your own machine.

  3. Upload it

    a minute enlist-deploy --control-plane https://enlist… --app LegacyInvoicing --source .\LegacyInvoicing

    Every warning appears here, before a server is touched.

  4. Place it

    two minutes Rule: role=finance · Running

    From the portal. It starts on every matching server within seconds.

  5. Retire the old wiring

    once per server Disable the scheduled task; remove the NSSM service

    The last time anyone needs to sign in to that server for it.

Nothing gets rewritten. Everything gets watched.
