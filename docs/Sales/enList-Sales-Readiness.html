enList v3 Sales brief To the enList team 15 Sep 2026

The engine is ready to sell. The product isn't yet.

We could sign a pilot with a friendly customer today, but we couldn't sell licenses at scale. That's not about code quality: the core is solid, with 348 test methods and a real install that deploys and runs apps through both container engines. The gap is that enList was built as an internal tool, and its own requirements doc still calls it one. A paying customer measures it against a different checklist.

Where we win

What a Windows shop hears in the first ten minutes, and can check is real.

  • Legacy and modern side by side.NET Framework 4.7.2 apps and .NET 10 apps, run and watched from one portal.
  • Outbound-only agentsManaged machines never open an inbound port. Security teams like hearing that.
  • Rules, not scriptsSay what runs where by tag. A new server matching the tag picks up its apps on its own.
  • Process or container, same packageNothing is rebuilt. Runs through wslc too, so no Docker Desktop license needed.
  • Control inside an appStop one service or job without restarting the whole application.
  • An installer that works unattendedProven by real installs, not just demos.
Real rival

What customers already have: Task Scheduler, service wrappers, remote desktop and scripts. Kubernetes and Nomad are too heavy for these shops, and Octopus deploys well but doesn't supervise what it deployed. Keeping background work running on Windows fleets is a real, underserved niche.

Where deals stall

A buyer's path, in the order they walk it, and where each stage stops today.

  1. Stage 1

    Try it

    Blocked

    enList only runs code written against our six attributes: [EnlistService], [EnlistJob] and the rest. A prospect's existing services, console programs and scripts can't be managed without rewriting them, so every evaluation starts as a developer project.

  2. Stage 2

    Security review

    Fails
    • Windows groups only, no Entra ID sign-in
    • Two roles: Operator and Viewer
    • No audit table, only log lines
    • No secrets store: settings are plain JSON
    • No alerts, no HA, no agent self-update
    • Installers aren't code-signed
  3. Stage 3

    Pilot

    At risk
    • A rollout hits every matching machine at once, with no health check
    • A service stopped in the portal starts again after a restart
    • Only a job's last run is kept, and there's no "run now"
  4. Stage 4

    Purchase

    Not built
    • No license key or EULA page in the installer
    • No pricing
    • No self-serve trial
    • No CI/CD examples
The next move

Generic workload mode

Let enList run any existing program unchanged, whether an .exe, a console app or a PowerShell script, either kept alive as a service or run on a schedule as a job.

It changes the pitch "Rewrite your apps to try us." "Point us at what you already run."
Everything we built applies at once
  • Tags and rules
  • Portal visibility
  • Restart with backoff
  • Process-tree cleanup
  • Log pipeline, from console output
  • Cron scheduling

Why it's first: a trial becomes an afternoon instead of a project, and the market grows from teams willing to adopt our SDK to every Windows shop.

What stays: the attribute SDK becomes the premium tier, since it gives per-service control and graceful stops. Container mode for arbitrary programs can wait; process mode is what these customers need first.

Alongside it, not after it

Sales

Three to five design partners

Windows-heavy companies in logistics, manufacturing and finance back offices, recruited on the promise of generic workload mode.

Engineering, in order

From pilot-safe to review-ready

  1. Portal stops that stick after a restart; job run history and "run now"
  2. Alerts (email, Teams, webhook), Entra ID sign-in, an audit table
  3. Gradual rollouts gated on health checks
  4. Agent self-update, licensing, code signing (certificate still to buy)
Pricing hypothesis

Per managed machine, per year

The norm in this category, and it grows as their fleet grows.
