enList Portal — Simplification Wireframe

Low-fidelity mockup — layout & concepts only, not final visual design. Everything about one application — its policy rules, where it's running, its old package versions — lives under that application. Only Applications, Agents, and Logs remain as top-level tabs.

The End-to-End Flow

1
Deploy — no target
$ enlist-deploy --app OrderProcessor --source ./bin/Release
# uploaded. not running anywhere yet.
The CLI's only job is publishing a package. It no longer takes --machines, --tags, or --desired-state — those don't exist yet at this point.
↓ Screen 1, Applications
→
2
Declare an Application Policy
In the portal, separately: "OrderProcessor's policy is env=test2 — any agent that qualifies runs it." This is the only place "which agents can run this" gets decided.
↓ Screen 3, OrderProcessor's policy
→
3
Watch it run
Expand the application's own row right on the Applications tab to see every agent it's running on, live — no separate tab to go find.
↓ Screen 1, Applications (expanded)
→
4
Disable it → it stops
Go back to that policy rule and disable it. The application isn't just "marked disabled" somewhere — it actually stops running, everywhere that rule qualified.
↓ Before / After, below

These are enList's OWN operating logs — the software's health, not any application's behavior. "OrderProcessor: requires runtime flavor..." above is the AGENT logging about its own reconciliation failure, which is fair game here; "Legacy Service: heartbeat 42" (something OrderProcessor itself printed) is not — that lives on the Applications tab now (📄 logs on its expanded panel, Screen 1), scoped to the one application and agent it came from.
No separate Running tab Folded into Applications instead: click a row (Screen 1) and it expands in place to show every agent currently running that application, live. One fewer top-level concept, and "where does this run" has exactly one home.
Excluding an agent — new A genuinely new capability, not something the shipped app has today: "Included/Excluded" on Screen 2, independent of Online/Offline (an agent can be online but excluded, or offline but still included). It's the one exception to "everything lives on the application" — this action is agent-scoped, not application-scoped, because it needs to apply across every rule that happens to reach this one box at once, without editing each of them.
No separate Application Policies tab either Same reasoning again: a policy rule belongs to one application, so it lives on that application's own screen (Screen 3), which now shows ALL of that app's rules as a list — not just one wizard for one rule. An application can have several rules (env=test2 AND a specific agent, say), each independently enabled or disabled.
Packages aren't first-class either A package is CLI plumbing (Step 1's output), not something worth a fleet-wide browsing tab. What's left of package management — deleting old versions nothing references — lives one click off the application's own screen (Screen 3c).
Agent vs. Machine "Agent" replaces "Machine" everywhere in the UI — it already matches the running component's real name (Enlist.Agent), so the vocabulary the user sees now matches the vocabulary in logs, error messages, and this documentation.
Application Policy, not Agent Policy "Agent Policy" reads ambiguously — it sounds like configuration that lives on an agent, not a rule about what an application does. "Application Policy" puts the right noun in front: it's OrderProcessor's policy, and its content happens to be agent-matching tags.
Logs stays a tab — but only for enList itself Unlike Running/Policies/Packages, Logs earns its place in the main nav: it's genuinely cross-cutting — Portal, Control Plane, and every Agent's own health, none of which belongs to one application. What an application prints (a service's heartbeat, a job's output) is that application's own data, so it moved to the Applications tab (📄 logs on the expanded panel, Screen 1) — the same consolidation as everything else here, just landing on the opposite side of one genuinely real boundary.
Reading this wireframe: boxes and spacing are illustrative, not pixel-accurate. Blue elements are the primary path; gray/dashed elements are supporting detail; red marks a stop/disable action. Nothing here is implemented yet — this is a discussion draft. Nav is now just three tabs: Applications, Agents, Logs.
